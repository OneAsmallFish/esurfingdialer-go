# FAQ

## 这是破解吗？

不是。它使用**你自己的账号和密码**，完成和你手机点"登录"完全一样的认证流程。
它不修改服务端数据、不伪造他人身份、不绕过计费。

## 为什么值得重写一个客户端？

因为官方客户端在路由器上跑不了，而这个场景（宿舍网关常在线、需要多线叠加）
恰恰是最需要它的地方。一个几 MB 的静态二进制能解决的事，没必要拖一个运行时。

## 会不会被封号？

任何自动化工具都有这个风险，我们无法替你保证。请阅读并遵守你所在学校 / 运营商
的规定。多拨尤其可能触发上游的并发策略。**风险自负。**

## 支持哪些学校？

凡是使用同一套 CCTP 认证链路的接入点都有可能工作，但**每个接入点的策略都不同**：

- 有的接入点会下发动态 ZSM 模块，有的用固定算法；
- 有的对 User-Agent 敏感（2093 vs 2089 会拿到不同模块）；
- 有的允许多会话，有的会静默互斥。

所以"能编译"和"能在你的学校用"是两件事。请先用单拨验证。

## 为什么我的第三个/第四个会话认证成功却上不了网？

见 [multi-dial.md 第 10 章](multi-dial.md#10-实测数据与容量规划)。这通常不是配置问题，
而是上游的数据面并发策略。认证层允许你上线，不等于数据面允许你转发。

## 需要 root 吗？

在路由器上需要（要绑接口 / 改路由表）。在普通 Linux 上如果不需要绑定特定接口，
普通用户也能跑。

## 为什么依赖只有 gmsm 一个？

因为 SM4 与 ZUC 是国密算法，标准库没有实现。其余全部用标准库完成，
包括 AES、DESede、MD5、SHA-256、HTTP、XML。依赖越少，交叉编译和审计越简单。

## 支持 IPv6 吗？

认证报文里的 `<ipv6>` 字段目前留空。上游普遍以 IPv4 为准。

## 能不能不写配置文件？

可以，全用命令行或环境变量：

```sh
ESURFING_USER=账号 ESURFING_PASSWORD=密码 ./esurfingdialer
```

但多实例场景强烈建议用配置文件 + `chmod 600`，避免凭据出现在 `ps` 输出里。

## 日志里为什么看不到 URL 的查询串？

因为查询串里带 `wlanuserip` / `wlanacip` 等环境信息，属于你的网络细节。
日志只保留 `scheme://host/path`。这是刻意的脱敏设计。

## 为什么 TERM 总是超时？

服务端释放会话慢。主动下线是 best-effort，超时不影响退出。详见
[troubleshooting.md 第 7 章](troubleshooting.md#7-退出时的-term-error)。

## 可以商用 / 集成到我的产品里吗？

GPL-3.0 允许商用，但它是 **copyleft**：你若分发修改后的版本，必须同样以 GPL-3.0
开源，并保留版权声明。此外请自行承担合规责任——特别是要让最终用户明确知道，
这是在用他们自己的账号接入。

## 怎么参与？

见 [CONTRIBUTING.md](../CONTRIBUTING.md)。最有价值的贡献是：
